## 10:37 分栏改造 + 详情标题（主人追加，已落地）

### 需求
1. 「Duo 内屏横屏那么大，不做平行视图或分列视图太浪费」→ 宽屏改 **NavigationSplitView**。
2. 详情页顶部标题写「详情」，不要写短信平台名。

### 实现（`PickupListView` / `HistoryView` 同构）
- `body` 用 `@Environment(\.horizontalSizeClass)` 分流：
  - `.regular`（Duo 展开）→ `splitLayout`；
  - 否则 → `stackedLayout`（原单栈，逐像素不变）。
- 抽出 `listPane`（List + 全部修饰：搜索/工具栏/侧滑/长按/多选/弹层），**`navigationDestination` 从 listPane 移出**，由两个布局各自挂到对应栈上（否则分栏下会被注册到无栈的 sidebar 列）。
- `splitLayout` = `NavigationSplitView { listPane } detail: { NavigationStack(path: $model.path) { SplitDetailPlaceholder().navigationDestination(...) } }`，导航仍由 `model.path` 驱动 → 列表点击只 append，多选/分享/侧滑/长按**一行都不用改**。
- 列宽：首版 ideal 340pt，**实测太窄**（30pt 取件码遇 `YT8861990771306` 顶到勾选圈）→ 改 `min 340 / ideal 380 / max 460`。
- `DesignSystem.swift` 新增 `SplitDetailPlaceholder`（`ContentUnavailableView`：「未选择取件码 / 从左侧列表点选一条，详情会显示在这一栏。」）。
- `RecordDetailView`：`.navigationTitle(record.company)` → **`"详情"`**（此前「拼多多发的圆通件」标题写拼多多，与卡内主名圆通自相矛盾）。
- 新增脚手架 `SIMCTL_CHILD_SPLIT_DETAIL=<码子串>`：启动即 `model.path.append(命中记录)`，用于命令行拍「左列表/右详情」联动（点卡片手势无法脚本化）。

### 实测结论（截图核对）
- Duo 展开：左侧 380pt 列表 + 右侧详情，标题「详情」正确；占位页、已取页、多选态均正常。
- **Duo 在 regular 下系统把标签栏渲染成右侧竖排图标列**（箱/勾/图表/齿轮），占 84pt —— 与 metrics 报的 `safe right=84` 是同一块；内容宽度 = 951 − 84。
- iPhone 16 Pro 窄屏：单栈、大标题、底部四标签、卡片全宽 370pt，与旧版一致。
- 构建：`BUILD SUCCEEDED`、**0 warning**。

### 工具经验（重要）
- **模型现在能直接读 PNG 截图**（`Read` 图片可返回图像）——此前"读不了图"的判断作废，布局验收应优先看图，别只靠像素统计。
- Duo 模拟器 `erase`/新建后会 `Data Migration Failed`，内屏不点亮（截图全黑、2007×2853 竖版）；解法：`open -a /Applications/Xcode.app/Contents/Applications/DeviceHub.app --args -CurrentDeviceUDID <udid>`（Xcode 27 已无 Simulator.app，宿主改叫 **DeviceHub**），GUI 打开后内屏即点亮，且端口 UUID 每次重启都会变，必须重新 `enumerate`。

## 11:30 Duo 外屏顶部操作栏「靠右」的排查结论（未改，已回退）

- 现象：外屏（466×678，compact）上，标题「待取」右侧的三枚按钮被系统并成一条玻璃胶囊，右缘几乎贴屏幕右缘；而卡片右缘因**右侧安全区**让开了约 30pt → 两者不齐，看着"探出去"。
- 实测两条路都无效（已回退，代码回到 `ToolbarItemGroup`）：
  1. 给工具栏内容加 `.padding(.trailing, 14/30)` —— **位置不变**（padding 只撑大胶囊内部，不移动胶囊）。
  2. 把三枚按钮合并成单个 `ToolbarItem` 再加 padding —— 胶囊位置同样不变。
- 结论：**iOS 27 的导航栏玻璃胶囊位置由系统决定**，没有可调的 padding/inset；导航栏不像内容那样避让外屏右侧安全区。
- 可选方案（待主人定）：
  - **A. 减少按钮**：把「选择」收进 ⊕ 菜单 → 胶囊从 3 项降到 2 项，宽度约减 40%，贴边感明显减弱（代价：多选入口深一层）。
  - **B. 自绘顶栏**：`.toolbar(.hidden)` + 顶部自绘，位置完全可控，但 `.searchable` 依赖导航栏，需自建搜索框（工作量大）。
- ⚠️ 顺带确认：**合并成单 `ToolbarItem` 不会让胶囊跑到标题上方**（先前判断有误），那本来就是 iOS 27 大标题导航栏的布局（按钮浮动在标题行上方右侧）。

### 13:16 「已取页面地址无法导航」—— 用错地理编码 API
- 现象：地址是「家佳福超市」（有效），地图仍显示「无法解析该地址」。
- 🔴 **根因：`MKGeocodingRequest(addressString:)` 是给「结构化街道地址」（省市区+门牌）用的**，
  拿「家佳福超市」「甘州院子店」这类**门店名 / POI 名**去问，它基本返回空
  → 所有驿站、超市类取件地址全部卡在「无法解析」。
- 修法：`resolveCoordinate` 改成**先 POI、后地址**两段式：
  1. `MKLocalSearch.Request().naturalLanguageQuery = address` —— 这才是 Apple 地图搜商户的 API，

  2. POI 搜不到（纯路名等）再退回 `MKGeocodingRequest`；
  3. 两个回调都 `DispatchQueue.main.async` 回主线程 —— 它们不保证主线程，

- 实测：同一张卡从「无法解析」变成正常地图，标记落在「家佳福超市」（张掖甘州区旧城山公园附近），导航按钮随之可用 ✓
- 教训：**MapKit 两套 API 分工不能混** —— 地址解析（Geocoding）≠ POI 搜索（LocalSearch），
  取件场景里绝大多数地址是"店名"，必须走后者。

### 14:08 水滴粘连 = 原生 `GlassEffectContainer`（主人：「原生组件难道不能实现吗」）

   拉伸 0 → 完全重合 = 正圆；拉伸 46 → 首尾相接 = 药丸；再拉 → 中间拉细 → 超过
   容器 `spacing`(26) → 水滴断开。**松手阈值就设在断开点附近**，语义极自然。
2. 外面包 **`GlassEffectContainer(spacing: 26)`** —— 它才是融合的施加者：
   按 spacing 自动让容器内的玻璃元素粘连/拉丝/断开（系统水银珠那套行为）。
3. 🔴 **绝对不要叠加 `glassEffectUnion`**（实测踩坑）：它的语义是「多个视图共用同一块
   玻璃**材质**」，会**吃掉后一个元素的几何** —— 结果只画出一个圆，粘连完全看不到。
   融合交给容器本身即可，union 是画蛇添足。
4. 🔴 **也不要用 HStack 负间距**凑重叠：容器内部会重算布局，负 spacing 无效（同样只画一个圆）。
   用 `offset` 只挪渲染位置，最可靠。
- 自定义 `DropletShape`（贝塞尔画腰部收窄）**已删除** —— 原生容器能做到就别手搓，
  自绘形状还有个硬伤：它只是"形状变长"，没有元素间的引力与断裂过程。
- 实测：stretch=40 时呈标准**花生形**（两瓣融合、中间平滑收窄）✓ 正是要的水滴粘连。
